# 학기 전체 로드맵 — 세션별 실행계획 (Week 3–10)

COSMOS PRJ-01. Week 1–2는 [`week-01-kickoff.md`](week-01-kickoff.md)가 이미 세션 단위로 상세히 짜놨다
— 이 문서는 **그 이후, Week 3부터 발표(Week 10)까지**를 같은 해상도로 잇는다. 두 문서를 합치면
학기 처음부터 끝까지 "이번 동아리 시간에 뭘 하나"가 끊기지 않는다.

**이 문서가 쓰인 이유**: `AGENTS.md`에 8–10주 매크로 로드맵(1–3주 기구·baseline / 2–5주 시뮬 / 6–7주
실기이식 / 8–10주 발표)은 있었지만, 그건 "몇 주차에 뭘"까지만 정해놓은 큰 틀이었다. 소프트웨어팀에게
"이번 주 동아리 시간에 정확히 뭘 하면 되냐"를 설명할 수 있는 세션 단위 계획이 없었다 — 이 문서가 그
빈 부분이다.

> **범위 경계**: 이 문서의 기구·전자 트랙 배치는 **팀 간 조율을 위한 상위 수준 배치**다(몇 주차에
> 마스터 설계도 §10/§9의 어느 단계를 하는지). 부품 조달 세부 일정, 프린트 큐 최적화, 실측 체크리스트
> 확장 같은 **더 세밀한 엔지니어링 실행 디테일은 별도 세션에서 보강**할 예정 — 이 문서의 주차 경계와
> 완료기준(exit criteria)은 그대로 두고, 그 안의 세부 태스크만 확장하면 이 문서와 충돌하지 않는다.

### 0.1 일정 리스크 — 매크로 로드맵과 실제 진행 상황의 차이 (먼저 읽을 것)

`AGENTS.md`의 원래 매크로 로드맵은 "1–3주차에 baseline(PID/LQR) 확보"를 가정했다. 그런데 2026-09-17
현재 상태 로그를 보면 **아직 Teensy 핀헤더도 안 납땜됐고, CAD STL도 export 안 됐고, 안전계획서 서명도
미확인**이다 — 이 상태에서 3주 안에 조립+전자+baseline 튜닝까지 끝내는 건 비현실적이다.

**이 문서는 낙관적 가정 대신 실제 진행 상황 기준으로 다시 짰다.** 그 결과:

- baseline(TC-3/TC-4) 확정 = **Week 7**(원래 목표: Week 3) — 약 4주 밀림
- RL 비교(TC-5) = **Week 8**(원래 목표: Week 6–7)
- 발표 준비에 **Week 9–10**, 2주 확보 — 빠듯하지만 가능

→ **부장 판단 필요**: ①이대로 8–10주 안에 압축해서 간다(TC-6·TC-7 저고도 홉은 가장 먼저 잘라낼 후보 —
마스터 설계도 §7 스코프 정의에도 "1차: 구속 자세 비교(주력) / 2차: 저고도 홉"이라 이미 우선순위가
낮게 잡혀 있다), 또는 ②학기를 11–12주로 늘린다. 아래 표는 ①(8–10주 압축) 기준으로 짰다 — ②를 택하면
Week 6부터 한 주씩 밀리기만 하면 되고 구조는 안 바뀐다.

### 0.2 추가 리스크 — RL 트랙 스코프 확장(2026-09-18)

`docs/design/03-control-pipeline-design.md`에서 RL 트랙 목표를 다시 잡았다: 지금 있는
`sim/sim_stage1/hopper_aviary.py`(numpy)는 파이프라인 PoC일 뿐이고, **진짜 목표는 3D 물리엔진
(PyFlyt 등) 기반 Stage 2로 전환하는 것**이다. 이건 원래 계획보다 작업량이 늘어난 것 — 아래 표의
"소프트웨어" 칸(Week 3~8, RL 학습 반복)은 **여전히 Stage 1 PoC 기준으로 짜여 있다.** Stage 2 전환
작업(물리엔진 후보 검증 →URDF 작성 → 재학습)을 정확히 몇 주차에 넣을지는 `03-control-pipeline-design.md`
§8의 팀 행동항목(특히 "PyFlyt 소스 직접 검증") 결과가 나와야 정할 수 있다 — **지금은 배치 안 함,
검증 결과 나오는 대로 이 문서를 갱신할 것.** 그 전까지는 Stage 1로 baseline 비교(Week 7–8)를 먼저
완성하는 걸 막지 않는다 — Stage 2는 그 위에 얹는 심화 확장으로 생각할 것.

### Week 4 — 만능기판 확정 + KiCad 스키매틱 캡처

**이번 주가 KiCad를 처음 쓰는 주다.** 순서가 중요 — 배선을 KiCad로 먼저 그리고 납땜하는 게 아니라,
**빵판에서 이미 검증된 배선(Week 3)을 KiCad로 옮겨 적는다.** 이유: 이 프로젝트는 맨땅에서 회로를
설계하는 게 아니라 이미 확정된 핀맵(`01-avionics-integration-final.md` §2)이 있으므로, KiCad는 새
설계 도구가 아니라 **"검증된 배선을 정식 도면으로 문서화"하는 도구**로 쓰는 것 — 조립 실수를 줄이고,
발표·인수인계 자료로도 남는다.

| 팀 | 세션 A | 세션 B |
|---|---|---|
| 기구·전자 | 만능기판 납땜(§5.4 순서: 장착홀 확공 → GND/+5V 버스 → Teensy 헤더 → 3핀헤더류 → IMU 소켓 → 캡) | 도통검사(멀티미터, §5.4-6) → Teensy 장착 → 레일전압 확인(§5.4-7) |
| **기구·전자(KiCad, 신규)** | — | **KiCad 스키매틱 캡처 착수**: `01-avionics-integration-final.md` §2.2(핀맵)·§5.3(만능기판 홀 좌표)를 그대로 회로도 심볼로 옮긴다. Teensy 4.0·BNO085·서보×4·수신기·ESC 심볼 배치 → 넷(net) 연결. **PCB 레이아웃까지는 안 감** — 스키매틱(회로도)만으로 충분(§4 참고) |
| 소프트웨어 | 웹 **W-B 차트 뼈대**(Chart.js, 가짜 PID/RL 두 시리즈 겹쳐그리기) | RL 학습 계속. 실험 A(추력곡선) 일정 확인 — 아직이면 params.yaml 대기 |
| 실험·운영 | TC-0(스로틀온리) 준비 | **TC-0 실행**(안전계획 서명 전제, 마스터 §11 합격기준) |

**완료기준**: ☐ 만능기판 도통검사 통과(단락 없음) ☐ KiCad 스키매틱 1차 완성(핀맵 100% 반영, §2.2 표와
넷 이름 1:1 대조 완료) ☐ TC-0 통과(진동·이상음·유격 이상 없음)

| 소프트웨어 | **TC-3·TC-4 반복** → baseline 데이터셋 확정 | RL 정책 **실기 이식 방법 결정**(§8.1-7 "`control_hover()`의 `output=K*error`를 정책망 추론으로 교체" 구조 — 추론을 Teensy 온보드에서 할지, 노트북에서 하고 시리얼로 서보값만 보낼지 **팀 논의 필요**, 아래 §6 참고) + 확정 params.yaml로 RL 재학습 |
| 실험·운영 | TC-4(외란 강인성) | TC-3·TC-4 데이터 정리 → `data/`에 baseline 확정본으로 저장 |

**완료기준**: ☐ baseline(PID/LQR) 데이터셋 확정 — 이게 RL과 비교할 기준선 ☐ RL 이식 방법(온보드 추론 vs
호스트 추론) 결정됨

## 4. 팀 간 의존성 (핵심 handoff 지점)

```
기구팀 실측(EDF·서보·만능기판) ──► CAD MEASURED 반영 ──► 전자 배치 확정 ──► KiCad 스키매틱(Week 4)
                                                              │
실험 A(추력곡선) ──► sim/params.yaml(Kf 등) ──► RL 재학습 ────┤
                                                              │
조립 후 질량·CG 실측 ──► sim/params.yaml(mass, Jxx/Jyy/Jzz) ──┤
                                                              ▼
펌웨어 통합(§4 CSV 스키마 반영) ──► TC-0~TC-5 실데이터 ──► 웹 대시보드(3D 리플레이 + 비교차트)
                                                              ▲
RL 학습 로그(같은 스키마 export) ──────────────────────────────┘

안전계획서 서명 ──► 모든 "전원 인가" 시험(TC-0 이후 전부)의 선행조건 — 타협 없음
```

**가장 자주 막히는 지점**: 펌웨어가 §4(CSV 스키마, `02-web-dashboard-design.md`)에 맞춰 `Serial.print()`
포맷을 찍지 않으면 웹팀이 실데이터를 못 받는다 — **통합 펌웨어 작성 시(Week 5~7 사이) 이 스키마를
`firmware/cosmos/` 담당자에게 미리 공유해둘 것.**

## 5. 부장 체크리스트 (매주 반복)

`week-01-kickoff.md` §7의 5원칙을 매주 그대로 적용:

1. **세션 시작 시 지난 주 완료기준부터 확인** (§3 각 주차 "완료기준" 체크박스)
2. **팀장에게 위임, 부장은 팀 간 연결점만** — 특히 §4의 handoff 지점(실측→params.yaml, 펌웨어→웹 스키마)
3. **완벽하게 하려다 멈추지 말 것** — 안 맞으면 조정, 일정 리스크(§0.1)를 매주 재확인
4. **안전은 타협 없음** — 서명 없이 EDF 전원 안 넣음, 모든 초기 시험 구속 상태
5. **모든 회의·시험·구매를 로그로** — Week 9의 발표자료가 여기서 나온다
