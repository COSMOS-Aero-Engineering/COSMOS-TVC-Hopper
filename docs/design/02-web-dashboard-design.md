# 웹 대시보드 · 3D 인터페이스 — 설계도 (신규, 2026-09-18)

COSMOS PRJ-01. **이 문서가 "소프트웨어팀 웹 산출물"의 단일 진실 소스다.**
`sim/`(RL 학습)·`firmware/`(실기 제어)는 이미 각자 README가 있는데, 이 프로젝트의 **세 번째 소프트웨어
축 — "PID vs RL 비교를 보여주는 웹 화면 + 우리 기체의 3D 인터페이스"** — 는 지금까지 "웹으로 구현할 생각"
한 문장 말고는 스펙이 하나도 없었다. 이 문서가 그 스펙이다.

**이 문서를 쓰는 이유**: 부장이 소프트웨어팀에게 "정확히 뭘 만들어야 하는지"를 설명 못 하고 있었다.
아래를 읽으면 ①왜 이게 필요한지 ②정확히 뭘 만드는지 ③어떤 데이터를 어디서 받는지 ④무슨 기술로
시작하면 되는지가 다 나온다.

## 1. 왜 이게 필요한가

홍보 발표(`docs/presentation/speaker-notes.md`, 2026-09-05)에서 이미 약속한 내용:

> "같은 하드웨어, 같은 임무 조건에서 PID와 강화학습 정책을 각각 올려보고, 복원 시간이나 정상상태 오차
> 같은 지표로 **정량적으로 직접 비교**하는 것이 이번 프로젝트의 진짜 핵심이고, 실제로 어느 쪽이 더 나은
> 성능을 내는지를 **데이터로 증명**하는 게 목표입니다."

"데이터로 증명"이 실제로 되려면 그 데이터를 **보여줄 화면**이 있어야 한다. 지금 상태:

- 데이터는 나온다 — Teensy가 USB 시리얼로 CSV를 찍는다(`01-avionics-integration-final.md` §3.5), RL
  학습도 로그를 남길 수 있다.
- 근데 그걸 볼 방법이 CSV 파일을 텍스트 에디터로 여는 것밖에 없다. **비교표·그래프·발표자료가 전부
  수작업**이 된다는 뜻.
- "3D 인터페이스"는 장식이 아니라 **디버깅 도구**이기도 하다 — TC-1(베인 방향 검증, 마스터 §11)에서
  "롤 명령 → 실제로 롤 방향 베인이 움직였나"를 눈으로 확인하는 게 지금은 사람이 기체를 보면서 확인하는
  방식뿐인데, 3D 뷰어가 있으면 로그만으로도 사후 검증이 된다.

**결론: 이 웹 앱이 곧 발표 핵심 자료(슬라이드 6 "비교 실험"의 실제 산출물)다.** 장식용 사이드 프로젝트가
아니라, 이게 없으면 "데이터로 증명"이라는 프로젝트의 핵심 약속을 못 지킨다.

### 1.1 이 문서의 3D와 RL 훈련용 3D 물리엔진은 다른 것이다 — 혼동 금지

소프트웨어팀 내부에서 제일 헷갈리는 지점이라 먼저 못박는다. RL 트랙에도 3D가 따로 있다
(`03-control-pipeline-design.md` §2, Stage 2 물리엔진 전환) — **이 문서의 3D 뷰어와는 목적이 다르다.**

| | 이 문서의 웹 3D 뷰어 | RL 훈련용 3D 물리엔진(`03-control-pipeline-design.md`) |
|---|---|---|
| 역할 | 이미 계산된 로그(CSV)를 **그대로 재생**한다 — 물리 연산 없음 | **물리를 계산**한다(충돌·강체동역학·공력) — RL이 학습하는 대상 |
| 언제 쓰나 | 시험 후/발표 시 결과를 보여줄 때 | 학습 중(팀 PC에서, 보통 헤드리스로 수백만 스텝) |
| 기술 | JavaScript + Three.js | Python + PyBullet(후보, §2) |
| 입력 | CSV의 이미 기록된 자세값 → 그대로 회전만 | RL 액션 → 물리엔진이 다음 상태 계산 |
| 공유 자산 | **같은 3D 모델(URDF/mesh)을 재사용 가능** — CAD 트랙이 STL을 한 번만 export하면 양쪽에서 씀 | 위와 동일 |

**한 줄 규칙**: 물리 계산이 필요하면 `03-control-pipeline-design.md`의 시뮬레이터, 그냥 보여주기만
하면 이 문서의 웹 뷰어. "RL을 3D로 한다"는 이 문서가 아니라 그 문서 얘기다 — 이 문서는 어디까지나
**결과를 보여주는 뷰어**.

## 2. 정확히 뭘 만드는가 (산출물 정의)

하나의 웹 앱(SPA) 안에 아래 3개 화면/기능이 들어간다. **셋 다 같은 CSV 데이터(§4)를 읽는다** — 데이터
소스가 하나라 화면만 3개인 구조.

### 산출물 A — 비교 대시보드 (발표 핵심)

- TC-3(baseline 안정화)·TC-4(외란 강인성)·TC-5(RL 비교) 로그를 불러와서:
  - 자세각(φ,θ,ψ) 시계열 그래프 — PID 런 vs RL 런을 **같은 그래프에 겹쳐서** 표시
  - 지표 요약 테이블: 복원시간(τ)·오버슈트·정상상태오차 (마스터 §11 TC-3 "합격 기준"과 동일 지표)
  - 여러 런(run)을 골라 비교(같은 시험을 N번 반복하니 평균·분산도 보여주면 좋음)

### 산출물 B — 3D 자세 뷰어

- 호퍼 형상(단순화된 3D 오브젝트, §5)을 화면에 띄우고, 로그의 자세값(쿼터니언 또는 φ,θ,ψ)에 맞춰
  **그 오브젝트를 실제로 회전**시킨다.
- **리플레이 모드**(기본, Stage 1) — CSV를 처음부터 끝까지 타임라인 슬라이더로 재생. 녹화된 시험을
  "다시 보기"하는 것.
- **라이브 모드**(스트레치, Stage 2 — ESP32 WiFi 붙은 뒤) — 실시간 텔레메트리를 받아 그 자리에서 회전.
  지금 당장 필요하지 않음(§6 로드맵 참고).

### 산출물 C — 시뮬레이션 뷰어 (RL 트랙과의 연결점)

- RL 학습 에피소드(지금은 `sim/sim_stage1/hopper_aviary.py`, 나중엔 `03-control-pipeline-design.md`
  §2의 Stage 2 물리엔진)도 **같은 스키마(§4)로 CSV export**하면 똑같은 3D 뷰어·차트로 볼 수 있다.
  "시뮬에서 배운 정책이 실기에서 어떻게 다르게 움직였나"를 나란히 보여줄 수 있음 — sim-to-real 격차를
  시각적으로 보여주는 발표 소재. **이때도 웹 앱은 물리를 다시 계산하지 않는다** — sim이 이미 계산해
  export한 CSV를 §1.1과 똑같은 방식으로 재생할 뿐이다.

**셋이 다 "같은 CSV 스키마를 읽는 뷰어"라는 점이 핵심 설계 원칙이다.** 소프트웨어팀이 처음에 헷갈리기
쉬운 지점 — "3D는 비행 시뮬레이터를 새로 만드는 건가?"가 아니라, **이미 있거나 앞으로 나올 로그 데이터를
읽어서 재생하는 뷰어**를 만드는 것이다. 물리 연산은 전혀 안 한다(그건 `sim/`이 이미 함).

## 3. 시스템 아키텍처

```
[데이터 소스]                    [프론트엔드 웹 앱]
 data/*.csv (Teensy USB 로그)  ─┐
 sim/.../episode_logs/*.csv    ─┼─►  CSV 파서 (§4 스키마)
 (STAGE 2) ESP32 WiFi 스트림   ─┘         │
                                          ├─► 산출물 A: 비교 차트 (Chart.js/Recharts)
                                          ├─► 산출물 B/C: 3D 뷰어 (Three.js)
                                          └─► 타임라인 슬라이더(리플레이 동기화)
```

- **Stage 1(지금 당장) = 백엔드 없음.** 브라우저가 CSV 파일을 직접 읽는다(파일 업로드 버튼 또는
  `fetch()`로 정적 파일 로드). 배포도 정적 호스팅(GitHub Pages)으로 충분 — 서버 관리·배포 파이프라인
  자체가 필요 없어서 **팀 리소스를 3D/차트 구현에 집중**할 수 있다.
- **Stage 2(ESP32 WiFi 텔레메트리 붙은 뒤, STAGE 2/3) = 경량 백엔드 추가 검토.** WebSocket으로 실시간
  중계가 필요해지면 그때 FastAPI(Python, RL 팀이 이미 익숙) 한 파일짜리 서버를 붙인다. **지금 미리
  만들지 않는다** — YAGNI, 실측 데이터도 없는데 실시간 인프라부터 만들면 우선순위가 뒤집힌다.

## 4. 데이터 계약 (Data Contract) — 펌웨어팀 ↔ 소프트웨어팀을 잇는 핵심

**이게 이 문서에서 제일 중요한 표다.** 펌웨어(`firmware/cosmos/`)가 이 컬럼 이름·순서로 CSV를 찍고,
웹 앱이 이 스키마로 파싱하면 두 팀이 서로 코드를 안 봐도 통합된다.

| 컬럼 | 단위 | 의미 | 출처 |
|---|---|---|---|
| `t_ms` | ms | 시험 시작 후 경과시간 | Teensy `millis()` |
| `mode` | 문자열 | `PID` \| `RL` \| `MANUAL` | 펌웨어가 현재 제어모드 태깅 |
| `phi`, `theta`, `psi` | rad | 자세각(roll/pitch/yaw), ZYX 오일러 | BNO085 쿼터니언→오일러 변환 (또는 쿼터니언 4개 원값도 같이 찍으면 §5-3에서 짐벌락 회피 가능) |
| `wx`, `wy`, `wz` | rad/s | 바디 각속도 | BNO085 자이로 |
| `servo1`..`servo4` | µs 또는 -1~1 | FWD/LEFT/AFT/RIGHT 베인 명령값 (`01-avionics-integration-final.md` §1 좌표 규약과 동일 순서) | 펌웨어 믹서 출력 |
| `throttle` | 0~1 | EDF 스로틀 | 펌웨어 DShot 명령 |
| `batt_v` | V | 배터리 전압 | ESC/ADC (있으면) |
| `rpm` | rpm | 로터 RPM (있으면, 자이로 정차 보정용) | 양방향 DShot 텔레메트리 |

- **파일명 규칙은 이미 확정돼 있다** (`01-avionics-integration-final.md` §3.5): `data/YYYYMMDD-TCx-런번호.csv`.
  웹 앱은 이 이름 패턴으로 시험(TC)·날짜·런을 자동 인식하면 편함(예: 파일 목록에서 TC별로 그룹핑).
- **지금 펌웨어 코드(`firmware/cosmos/imu_test/`, `throttle_serial/`)는 이 스키마로 안 찍고 있다** —
  통합 펌웨어(마스터 설계도 §8.1) 작성 시점에 `Serial.print()` 포맷을 이 표에 맞추는 작업이 필요하다.
  **이건 이 문서가 아니라 펌웨어 통합 작업의 할 일 목록에 들어간다** — 여기서는 "받을 형식"만 못박아둔다.
- sim 쪽(`sim/sim_stage1/`)도 학습 에피소드를 이 컬럼명으로 export하는 유틸이 하나 필요하다
  (`mode=RL`, `servo1..4`는 `hopper_aviary.py`의 `a1..a4`를 그대로, `throttle`도 동일 — 이미 5차원
  액션 구조가 이 스키마와 거의 1:1이라 변환이 쉽다).

## 5. 3D 오브젝트 — 무엇을 어떻게 렌더링하나

### 5.1 형상 — 처음부터 실제 CAD를 쓰지 않는다

- **Stage 1(지금 시작)**: 프리미티브 조합 — 원통(EDF 하우징) + 링(베인링) + 얇은 박스 4개(베인, 90°
  간격) + 가는 실린더 4개(다리). 비율은 `cad/hopper_params.scad`의 `edf_housing_od`·`vane_ring_od`·
  `foot_circle` 등 기존 상수를 그대로 가져다 쓰면 실제 기체 비율과 맞는다 — **새로 재는 게 아니라
  이미 정해진 숫자를 옮기기만 하면 됨.**
- **Stage 2(여유되면)**: `cad/print_parts/*.stl`(§9-0 export 파이프라인이 이미 있음, `cad/print_parts/README.md`)을
  Three.js `STLLoader`로 그대로 불러오기. CAD가 갱신되면 3D 뷰어도 자동으로 최신 형상이 된다.
  **선행조건**: STL이 실제로 export돼 있어야 함(2026-09-17 기준 아직 안 됨, `cad/README.md` 참고) — 그
  전엔 Stage 1 프리미티브로 충분하다.

### 5.2 자세 매핑

- BNO085가 **쿼터니언을 직접 출력**한다(마스터 설계도 §6.5) — 오일러각으로 변환했다가 다시 3D 회전에
  쓰면 짐벌락 근처에서 오차가 생긴다. **가능하면 CSV에 쿼터니언 4개(`qw,qx,qy,qz`)를 원값으로 같이
  찍어서, 3D 뷰어는 그걸 Three.js `Quaternion`에 직접 대입**하는 쪽을 권장(§4 표에 옵션 컬럼으로 추가
  가능). 오일러각(φ,θ,ψ)은 차트(산출물 A)용으로는 그대로 유용하니 둘 다 찍어도 된다.
- 좌표계는 `01-avionics-integration-final.md` §1의 방위 규약(+X=FWD/0°, +Y=LEFT/90°...)을 그대로 따른다
  — Three.js 좌표계(Y-up)와 축이 다르므로 **한 번만 변환 함수를 만들어두면 나머지는 신경 안 써도 됨**.

### 5.3 베인 애니메이션

- `servo1..4` 값을 베인 박스의 회전각으로 매핑 — 이것도 TC-1(베인 방향 검증) 디버깅에 바로 쓸모 있다
  (부호가 반대면 3D 뷰어에서 바로 티가 남).

## 6. 단계별 개발 로드맵 (소프트웨어팀 웹 서브트랙)

RL 서브트랙(`sim/`)과 **병렬로, 실측 데이터를 기다리지 않고 지금 바로 착수 가능**하다는 게 핵심 — 실제
주차 배치는 [`semester-roadmap.md`](../execution/semester-roadmap.md)에 있다. 여기서는 이 트랙 자체의
단계만 정의:

| Phase | 할 일 | 선행조건 |
|---|---|---|
| **W-A 뼈대** | Vite 프로젝트 세팅, Three.js로 프리미티브 호퍼 형상 띄우기, 가짜(합성) CSV로 회전 애니메이션 동작 확인 | 없음 — **지금 바로 시작 가능** |
| **W-B 차트** | Chart.js/Recharts로 시계열 그래프 뼈대, 가짜 데이터로 PID vs RL 두 시리즈 겹쳐 그리기 | W-A와 병렬 가능 |
| **W-C 실데이터 연결** | §4 스키마 확정 → 실제 CSV 파서로 교체(TC-0/TC-1 로그로 첫 검증) | 실험 A/B/C 데이터 존재 (기구·전자·실험팀 산출물) |
| **W-D 지표 계산** | 복원시간·오버슈트·정상상태오차를 코드로 자동 계산(사람이 눈으로 재지 않게) | TC-3 데이터 |
| **W-E 비교 완성** | TC-3(PID) vs TC-5(RL) 나란히, 요약 테이블 + 발표용 내보내기(PNG/PDF export) | TC-5 데이터, 이게 발표 핵심 자료 |
| **W-F (스트레치)** | 라이브 모드(WebSocket), STL 실형상 교체 | ESP32 텔레메트리, STL export 완료 |

## 7. 기술 스택 추천

| 레이어 | 추천 | 이유 |
|---|---|---|
| 빌드 도구 | **Vite** | 설정 거의 없이 바로 시작, HMR 빨라서 동아리 세션 중 실습에 적합 |
| 언어 | **JavaScript(또는 TypeScript)** | 3D/차트 라이브러리 생태계가 압도적으로 JS 쪽. TS는 팀이 타입에 익숙하면 버그를 미리 잡아줌(선택) |
| UI 프레임워크 | **바닐라 JS로 시작 → 필요하면 React 추가** | 팀 대부분이 Python(RL) 경험은 있어도 React 경험은 없을 수 있음. 화면이 3개뿐이라 처음엔 프레임워크 없이도 충분 — 나중에 상태 관리가 꼬이기 시작하면 그때 React 도입(과설계 방지) |
| 3D | **Three.js** | 압도적 1위 생태계, 한국어 튜토리얼도 많음. `OrbitControls`(마우스로 시점 회전)·`STLLoader`(§5.1) 내장 |
| 차트 | **Chart.js** (또는 Recharts, React 쓰면) | 시계열 겹쳐그리기·줌 플러그인 있음, 설정 간단 |
| CSV 파싱 | **PapaParse** | 헤더 자동 인식, 대용량도 스트리밍 파싱 가능 |
| 배포 | **GitHub Pages(정적)** | 저장소가 이미 GitHub — 별도 서버 없이 `main` 브랜치에서 바로 배포 가능(Stage 1 한정) |

이 조합의 공통점: **전부 무료·설정 최소·튜토리얼 풍부** — 동아리 세션 시간(1~3시간)에 실습으로 소화
가능한 난이도로 고른 것. React/백엔드가 필요해지는 시점은 §6 W-F 이후로 미뤄둔다.
