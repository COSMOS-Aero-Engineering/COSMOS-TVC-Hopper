# 제어 파이프라인 심화 설계 — PID·RL 아키텍처, 3D 시뮬레이션, 온보드 이식

COSMOS PRJ-01. **이 문서가 "PID/RL 제어를 정확히 어떻게 만들고 어떻게 실기에 올리는가"의 단일 진실
소스다.** `sim/sim_stage1/`(현재 구현)이 최종 목표가 아니라 **파이프라인이 도는지 확인하는 PoC**라는
점, 그리고 그 다음 단계(3D 물리엔진 전환·아키텍처 선택·온보드 배포)가 여태 문서화가 안 돼 있었다 —
이 문서가 그 공백이다.

**이 문서가 생긴 이유(2026-09-18)**: 부장이 "이 프로젝트는 이미 대학급 수준이니 PID·RL도 수준급으로
만들 생각"이라며 심화 리서치(§7의 출처)를 제공, `sim_stage1`을 최종 답이 아니라 테스트 단계로 재정의.
아래는 그 리서치를 **직접 검증하고**(§7에 검증 상태 표시) COSMOS 기체에 맞게 구조화한 것.

> **튜토리얼이 아니다.** "어떻게 설치하고 어떻게 코딩하는지"는 여기 없다 — 그건 다음 단계(부장 표현:
> "일단 튜토리얼 만드는 건 재껴두고"). 이 문서는 **뭘 선택하고 왜, 뭘 아직 검증 안 했고 누가 언제
> 검증할지**를 정하는 설계도다. 소프트웨어팀 차장이 이 문서를 읽고 §8(팀 행동항목)부터 시작하면 된다.

## 1. 목표 재확인

- **Stage 1(`sim/sim_stage1/hopper_aviary.py`, 완료)은 파이프라인 검증용 PoC다.** numpy로 직접 적분한
  단순화 모델 — 실제 물리 신뢰도가 낮고(공력 lumped 근사, 서보 동특성 없음, 충돌·접촉 없음), 목적은
  "SB3·gymnasium 연동이 우리 기체 상태/액션 구조로 정상 동작하는가"였을 뿐이다. **이 자체를 최종 학습
  결과로 쓰지 않는다** — 이미 `sim/README.md`·`hopper_aviary.py` 주석에도 명시돼 있던 원칙을 여기서
  다시 못박는다.
- **진짜 목표**: 실물 CAD/치수를 반영한 **3D 강체 물리엔진** 기반 시뮬레이션에서 학습하고, 학습된
  정책을 실제 온보드 비행 컴퓨터(Teensy 4.0)에 이식해서 baseline(PID/LQR)과 정량 비교한다 — 이게
  `AGENTS.md`가 원래부터 약속한 것과 같은 목표이되, **더 깊은 리서치·검증을 거쳐 실행**한다.
- 3D는 두 군데서 쓰인다 — **혼동하지 말 것**:

### 1.1 두 개의 "3D" — RL 훈련용 물리엔진 vs 웹 뷰어

| | RL 훈련용 3D 물리엔진 (이 문서) | 웹 3D 뷰어 (`02-web-dashboard-design.md`) |
|---|---|---|

**한 줄 규칙**: 물리 계산이 필요하면 이 문서(§2)의 시뮬레이터, 그냥 보여주기만 하면 `02번 문서`의

### Stage 1 — numpy 커스텀 env (완료, PoC로 유지)

- `sim/sim_stage1/hopper_aviary.py`. **버리지 않는다** — 물리엔진보다 100~1000배 빠르고 의존성이

### Stage 2 — 3D 물리엔진 전환 (신규 목표, 착수 전)

**후보 비교** — `AGENTS.md`가 2026-09-14에 gym-pybullet-drones를 이미 한 번 검토·기각했다(이유: 모터

| 후보 | 물리엔진 | 검증 상태(2026-09-18) | 판단 |
|---|---|---|---|
| **PyFlyt** (`jjshoots/PyFlyt`) | PyBullet | **문서 확인함(WebFetch로 공식 문서 읽음), 소스코드 레벨 검증은 아직** — `Motors`·`Gimbals`(짐벌/TVC)·`LiftingSurfaces`(공력면, 베인에 대응 가능)를 **모듈로 조합**해 "임의 구성의 UAV"를 만드는 구조라고 문서에 명시돼 있음(biplane·quadcopter·rocket 등). 내장 `Rocket` 드론 타입도 있음. | **가장 유망한 1순위 후보** — gym-pybullet-drones가 기각된 이유(하드코딩된 대칭 믹싱)가 여기엔 없어 보임(모듈형이라). **단, "보여 보인다"와 "실제로 된다"는 다르다 — §8 행동항목대로 팀이 `PyFlyt/core/drones/` 소스를 직접 읽고 EDF 1개+베인4 구성이 정말 포크 없이 되는지 확인 후 확정할 것.** |
| **gym-pybullet-drones** | PyBullet | 기각 유지(2026-09-14 검토, `AGENTS.md` 참고) | 재검토 안 함 — PyFlyt가 이미 이 문제를 모듈화로 풀어놓은 것으로 보여서 우선순위 낮음 |
| **커스텀 PyBullet + URDF 직접 구현** | PyBullet(raw) | 검증 불필요(우리가 직접 짜는 것) | PyFlyt가 막히면(§8) 이게 폴백 — PyBullet은 저수준 API가 자유로워서 "모터1+베인4"를 처음부터 우리 식대로 짤 수 있음. 단, 접촉·공력·모터 동역학을 전부 손으로 구현해야 해서 개발 비용 가장 큼 |

**CAD→물리엔진 자산 경로(이미 있는 파이프라인 재사용)**:
```
cad/hopper_params.scad(OpenSCAD, 정본)
   → STL export(cad/print_parts/, 이미 있는 워크플로 — cad/print_parts/README.md)
```

**새 CAD 도구가 필요한 게 아니다** — 이미 확정된 `hopper_params.scad`와 실측 질량속성을 XML 한 겹으로

선행조건은 STL export 완료**.

## 3. 제어 아키텍처 — 직접비교(Swap) vs Residual RL

두 가지 서로 다른 질문에 서로 다른 구조가 맞는다. **섞어서 생각하면 안 된다.**

| | 직접비교(Swap) — 현재 `AGENTS.md` 프로토콜 | Residual RL — 리서치가 제안한 구조 |
|---|---|---|
| 질문 | "PID가 나은가 RL이 나은가?" (발표에서 이미 약속한 핵심 질문) | "실기에서 안전하게, 성능을 더 짜낼 수 있는가?" |
| 구조 | 제어 블록을 **통째로 교체** — 한 런은 순수 PID, 다른 런은 순수 RL 정책 | `output = PID_output + RL_Δ` — RL은 PID가 이미 만든 출력 위에 **보정치만** 더함 |
| 장점 | 결과가 "PID vs RL" 프레이밍과 정확히 일치, 발표 스토리 그대로 씀, 구현 단순 | RL이 발산해도 PID가 베이스를 잡고 있어 더 안전, sim-to-real 격차에 강함(RL이 배워야 할 몫이 작음) |
| 단점 | RL이 처음부터 전부 배워야 해서 sim-to-real 격차에 더 취약 | "AI가 사람보다 나은가"라는 원래 질문과 프레이밍이 어긋남(RL 단독 성능을 안 보여줌) |
| **권장** | **Phase A(우선)** — 학기 핵심 산출물은 이거다. `semester-roadmap.md` Week 7–8이 이 구조 기준 | **Phase B(여유 시 확장)** — Phase A 완료 후, "그럼 더 안전한 실전 버전은?"이라는 후속 질문으로 붙이면 발표에서 오히려 깊이를 더해줌 |

**결론**: 지금 로드맵(`semester-roadmap.md`)은 안 바꾼다 — Phase A(직접비교)가 기본 경로. Residual RL은
Week 9(여유 주차)의 확장 옵션으로 `semester-roadmap.md` §3 Week 9 표에 추가해뒀다.

## 4. State / Action Space — 스테이지별로 다르다

`00-hopper-master-design.md` §9의 낡은 12차원/4차원 표(rev B 잔재, 실제 코드와 이미 안 맞았음)는
**폐기하고 이 표가 정본이다.**

### Stage 1 (구속, 자세만) — 이미 구현된 그대로, 안 바뀜

```
관측 obs (6): [phi, theta, psi, wx, wy, wz]      — 자세각 + 바디 각속도
행동 act (5): [a1, a2, a3, a4, throttle]          — 베인4 + 스로틀
```
위치를 안 재는 이유: 만능조인트로 구속돼 있어 위치가 상수다(재도 정보량이 0). 이 스펙은 그대로 유지.

### Stage 2/3 (자유비행, 위치·속도 포함) — 리서치 제안 채택

```
상태 S = [px,py,pz, vx,vy,vz, qw,qx,qy,qz, wx,wy,wz, θ_vane1..4]   (16차원)
행동 A = [Δα1,Δα2,Δα3,Δα4, T_throttle]                              (5차원, Residual RL이면 Δ, 직접비교면 절대값)
```

- 쿼터니언(qw,qx,qy,qz)을 쓰는 이유: 오일러각은 짐벌락(θ=±90°) 특이점이 있음 — Stage 1은 소각도
  근처만 다뤄서 문제없었지만, Stage 2/3는 큰 자세 변화를 다룰 수 있어 쿼터니언이 안전하다.
- **위치·속도(px,py,pz,vx,vy,vz)는 STAGE 3+ 센서(VL53L1X ToF + PMW3901 광류, BOM B7/B8)가 붙어야
  실기에서 측정 가능** — `00-hopper-master-design.md` BOM 계획과 이미 맞물려 있다. Stage 2 시뮬레이션
  자체는 (센서 없이) 물리엔진이 위치를 그냥 알려주므로 먼저 진행 가능, **실기 이식은 그 센서가 붙은
  뒤에나 의미 있다** — 순서를 착각하지 말 것.
- 베인 현재각(θ_vane1..4)을 상태에 포함하는 이유: 서보에 지연(§5)이 있어서, "명령한 각도"와 "실제
  각도"가 다를 수 있다 — 정책이 그 차이를 알아야 더 정확히 제어할 수 있다.

## 5. Domain Randomization — 현재 구현과의 갭

`sim/sim_stage1/params.yaml`의 `domain_rand` 블록(현재값)과 리서치 제안값을 대조한 표. **이미
`00-hopper-master-design.md` §9 rev B 표에 "서보지연 20~60ms"가 언급돼 있었는데, 실제로 코드에 구현된
적이 없다** — 발견한 갭이라 여기 기록해둔다.

| 파라미터 | 현재(`params.yaml`) | 리서치 제안 | 반영 상태 | 비고 |
|---|---|---|---|---|
| 질량·관성(Jxx/Jyy/Jzz) | ±30% | — | 구현됨 | 유지 |
| 베인 모멘트암 | ±15% | — | 구현됨 | 유지 |
| 추력계수 Kf | ±20% | — | 구현됨 | 유지 |
| **CG 오프셋** | **±3mm** | **±5~15mm** | 구현은 됐으나 **범위가 리서치 제안보다 좁음** | 조립 공차를 실측(§8-4, `01-avionics-integration-final.md` §8.2)한 뒤 그 실측 오차 범위로 다시 정할 것 — 지금 3mm는 근거 없는 임시값 |
| **서보 반응 지연** | **미구현** | **20~60ms** | **갭 — Stage 2에서 반드시 추가** | 액추에이터 동특성 자체가 `hopper_aviary.py`에 없음(명령 즉시 반영). 물리엔진 전환(§2) 시 1차 지연 필터로 추가 |
| **바람 외란/돌풍** | 미구현 | 무작위 외란 토크 | STAGE 1(구속)엔 불필요, STAGE 2/3(자유비행)에 필요 | 구속 시험은 실내·저속이라 우선순위 낮음 — Stage 2 물리엔진 전환 시 검토 |
| **추력 감쇄(배터리 전압강하)** | 미구현 | 배터리 전압에 따른 추력 저하 | 권장 추가 | `01-avionics-integration-final.md` §3.2 전류예산과 연동 가능(전압 새그 실측치 있으면 그대로 반영) |

| 경로 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. ONNX → TFLite Micro** | PyTorch/SB3로 학습한 PPO Actor를 ONNX export → TFLite Micro 런타임으로 Teensy에서 추론 | 표준 툴체인, 모델 구조 바뀌어도 재작업 적음 | TFLite Micro 라이브러리 의존성 추가, 빌드 복잡도 ↑ |
| **B. 수동 C++ 행렬곱** | 학습된 가중치(작은 MLP, 예: 은닉층 2개×64노드)를 배열로 export → Teensy에서 직접 forward pass(행렬곱 몇 줄) | **의존성 없음**, 코드가 30~50줄 수준, 디버깅 쉬움 | 모델 구조 바뀔 때마다 손으로 다시 export |

**조사 결과(2026-09-18, WebSearch로 확인)**: TFLite Micro는 Teensy 4.0에서 커뮤니티 예제로 이미
동작 확인됨(MNIST 추론 등), 작은 MLP 기준 서브-밀리초(1ms 미만) 추론이 보고됨. 우리 정책망은 그보다도
훨씬 작을 가능성이 높아(관측 6~16차원, 행동 5차원) **경로 B(수동 구현)도 충분히 현실적** — 오히려
학생 팀에게는 "왜 이게 동작하는지 눈으로 보이는" 경로 B가 디버깅·이해 측면에서 유리할 수 있다.
**권장: 경로 B를 먼저 시도, 안 풀리면 경로 A로.**

### 6.2 제어 루프 주기

작은 MLP는 10~50µs 수준 추론이 가능하다는 근거가 있어(§7 원 리서치 + 위 조사), Teensy 4.0(600MHz)
기준 **100Hz 이상 제어 루프**가 무리 없이 나온다 — 스톡 SolidGeek 코드의 제어 루프 주기와 비교해
병목이 안 됨을 확인할 것(`firmware/reference/SingleRotorUAV/src/control.cpp` 루프 주기 실측, Stage 3
착수 시).
